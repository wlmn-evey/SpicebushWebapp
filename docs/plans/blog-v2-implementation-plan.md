## 1. V1 Invariants (the hard gates every PR is regression-tested against)

These are the non-negotiable properties carried from the ledger, restated as concrete, regression-gated assertions. Every phase PR keeps them green in CI.

1. **The 6 live posts keep their URLs, content, categories/tags, and bylines.** URLs are immutable. `data.body` is converted ONCE from markdown to HTML (ADR-009 owner override 2026-06-07: HTML storage) by a late, verified Phase-1 migration whose gate is **rendered-output equivalence** — the public `.blog-body` render of the converted HTML is byte-equal (or equal after the bounded enumerated normalization allowlist of §5.4, which may never drop an element) to the pre-conversion markdown render — so content is preserved through the conversion, not untouched-in-storage; the migration snapshots each live row's markdown into a transient per-row backup BEFORE overwriting, and **rollback re-writes that backup into `data.body` together with the code-revert — code-revert alone is NOT a rollback (it would serve literal HTML); git history (migration 015) is only a stale secondary source for owner-edited rows** (D1-F4, see §5.4). Categories/tags are preserved on edit (Phase-1 PR0 prerequisite — V1 stores but does not preserve them on the upsert path, see §2). Bylines render each row's `data.author` string through the new author resolver via the legacy fallback (R4-F9, §2). Any `mailto:`/`tel:`/site-relative body links survive (sanitizer policy, invariant #3).
2. **Draft invisibility.** Draft, scheduled, and archived posts are invisible on every public surface. The live read filter is an exact-match `WHERE status = 'published'` (`content.ts:81,103`); Phase 2 hardens this with a DB `CHECK` constraint (R4-F2, §11 Phase 2).
3. **Sanitizer rigor equivalent-or-stronger, AND render-time sanitization is the non-negotiable guard.** Under HTML storage (ADR-009 override) the render path is **stored HTML → `DOMPurify.sanitize(STRICT_CONFIG_V2)` → `.blog-body`** (`renderPostBody`, `blog-content.ts:364`; `marked` no longer runs at render time — it survives only inside the one-time markdown→HTML conversion migration, §5). **Sanitize-on-write is NOT sufficient and MUST NOT replace render-time sanitization:** every render re-sanitizes, so a config tightening or a write-path bug can never serve stored XSS. Sanitize-on-write (at the AI/human insertion boundary) is permitted only as ADDITIONAL hygiene. `STRICT_CONFIG_V2` is the V1 config plus a BOUNDED delta for the TipTap construct set (full config and trust-boundary statement in §5/§7); the V1 properties re-asserted in CI carry forward unchanged where the delta does not touch them: (a) **no `id`**; (b) **fragments stripped**; (c) **body URI policy** `ALLOWED_URI_REGEXP = /^(?:https:|mailto:|tel:|\/(?![/\\]))/i` — `https:`/`mailto:`/`tel:`/site-relative allowed, **NOT "HTTPS-only"** (tightening to https-only is FORBIDDEN — it breaks live posts' mailto/tel links, R3-F1); (d) `ALLOW_DATA_ATTR` and `ALLOW_ARIA_ATTR` both `false`. The V2 delta adds only: a few tags (`u`, the `table`/`thead`/`tbody`/`tr`/`th`/`td`/`colgroup`/`col` family, `s`), an ENUMERATED `class` allowlist (code-block `language-*` + the four text-align classes), enumerated `target`/`rel`, and `colspan`/`rowspan` table-cell attributes (`colwidth` is NOT allowlisted — `resizable:false` tables never emit it, D1-F3) — and crucially does **NOT** un-ban the `style` attribute (class-based text-align; `resizable:false` tables — see §5). The featured-image `IMAGE_SCHEME_REGEX` (`blog-content.ts:45`, `/^(\/(?![/\\])|https:\/\/)/`) is a DISTINCT, stricter validator and must not be reused for body links or ticker hrefs.
   - **ACTIVATED constraint (R2-F4 — was deferred under markdown storage, now ACTIVE under HTML storage):** `collectBodyImageAlts` (`blog-content.ts:253`) walks markdown `image` tokens only. Under markdown storage this covered the whole body; under **HTML storage `data.body` now contains `<img>` tags** (TipTap emits `<img src alt title>` natively), which `collectBodyImageAlts`'s markdown-token walk does NOT see — so the alt-quality gate would silently miss every body image. The HTML escape hatch the prior plan said "no current path admits" IS the current path. **Phase 1 therefore replaces/augments `collectBodyImageAlts` with an HTML-aware alt gate** (DOM-walk the sanitized HTML's `<img>` nodes for missing/empty `alt`) BEFORE the editor is adopted; the converted 6 posts and all new TipTap/AI output flow through it (recorded §5).
4. **Cache staleness ≤5 min, preserved-or-improved-with-rationale.** Collections cache at `DEFAULT_COLLECTION_TTL = 5 min` (`content.ts:28`); `settings` caches at `SETTINGS_TTL = 30 min` (`content.ts:29`). Ticker + virtual-author keys live in `settings`, so a 5-min special-case read path is added (R4-F11, §10/§11 Phase 6) so they are not 6× staler than the analogous AnnouncementBar 5-min strip.
5. **Supervised rollout boundary.** Agents never mutate prod; every merge to main auto-deploys; the owner supervises merges; per-step stacked PRs within a phase; an owner checkpoint between phases.
6. **Gates green per PR:** `lint --max-warnings=0` + typecheck + full vitest + `format:check` + build. Run single test files during dev; full suite before commit.

## 4. Cross-Cutting Architecture Notes

- **One render path — non-negotiable.** Every body — TipTap output, AI body output, the converted 6 legacy posts — is stored HTML and renders through exactly one path: **stored HTML → `DOMPurify.sanitize(STRICT_CONFIG_V2)` → `.blog-body`** (`renderPostBody`). There is no second render path to audit. **Render-time sanitization is the guard and stays the guard:** storing HTML must NOT shift the trust boundary to sanitize-on-write-only — every render re-sanitizes, so tightening the config or fixing a write-path bug instantly protects already-stored content. `marked` is no longer in the render path; it runs only inside the one-time markdown→HTML conversion migration (§5). The markdown-source toggle is DROPPED (it presupposed markdown storage); TipTap's WYSIWYG surface is the single authoring path.
- **Shared Layout `<head>` extension (Phases 3+4).** A per-page `robots`/`noIndex` prop on `Layout.astro` and a `noindex, follow` third state in `resolveSeoMetadata` (driving BOTH `meta[name=robots]` at `Layout.astro:65` AND the conditional `meta[name=googlebot]` at `Layout.astro:66`), plus a JSON-LD/`<head>` slot for per-post structured data and RSS auto-discovery. This is one cross-cutting Layout+seo-config extension shared by Phase 3 (robots third state) and Phase 4 (JSON-LD/RSS link).
- **Canonical resolver reality.** `resolveSeoMetadata` strips the query string (`normalizePathname` → `withoutHash.split('?')`, `seo-config.ts:146`) and builds `new URL(normalizedPath, siteOrigin)`. Category index pages MUST therefore be PATH segments `/blog/category/[slug]` — a query-param shape would collapse every category canonical to `/blog` and break the ≥2-member design (R4-F15).
- **Auth fixture.** The required authenticated-browser Playwright fixture bootstraps via `context.addCookies` with `name:'sbms-admin-session'` and exact attributes matching the live session cookie (`auth/callback.astro:73-77`: path '/', httpOnly true, sameSite 'lax', secure on HTTPS). V1's only authed-E2E precedent uses a request-context Cookie header that bypasses cookie-attribute matching and does NOT prove page-level auth — hence the explicit PR2 spike (R4-F22).

## 5. Storage & Editor (Phase 1) — TipTap HTML Storage (ADR-009, owner override 2026-06-07)

The TipTap storage fork is **resolved in ADR-009: TipTap as the editor with HTML storage.** This reverses the prior ADR-009 decision (Markdown round-trip / Option B) on an explicit owner override of 2026-06-07: *"fix the plan to produce the fully functional html data like tiptap wants. I would rather have it correct."* This is the better engineering choice, not a concession: **TipTap is HTML-native** — its `getHTML()`/`setContent(html)` are the first-class API, and the markdown round-trip was the fragile bolt-on (`@tiptap/markdown` carried its own fallback escape hatch). Storing HTML removes the lossy serializer entirely and makes **underline, text-align, and TABLES first-class WYSIWYG** (the markdown-source-toggle deferral for tables is DROPPED). Post bodies are TipTap HTML in `data.body`; on load `editor.commands.setContent(storedHtml, { parseOptions: { preserveWhitespace: 'full' } })` hydrates the editor; on save `editor.getHTML()` is sanitized and written. The work is to do the bounded HTML adoption CORRECTLY. Binding decisions (full rationale in ADR-009):

### 5.1 One render path; render-time sanitization is the guard

Stored HTML → `DOMPurify.sanitize(STRICT_CONFIG_V2)` → `.blog-body`. **Render-time sanitization is non-negotiable and is the trust boundary** (§1 invariant #3, §7): every render re-sanitizes, so config tightening or a write-path bug can never serve stored XSS. Sanitize-on-write at the AI/human insertion boundary is permitted as ADDITIONAL hygiene but does NOT replace render-time sanitization. `marked` is no longer in the render path — it runs ONLY inside the one-time conversion migration (§5.4).

### 5.2 The new trust boundary: a few more tags + an ENUMERATED class allowlist, NO `style` attribute

The bounded delta from V1's `STRICT_CONFIG` is the smallest set that admits TipTap's StarterKit + underline + text-align + tables, audited against TipTap v3's actual emission. **Per the owner's class-based-not-style-based preference, the live config keeps the `style` attribute BANNED** and resolves text-align via a small fixed CLASS allowlist. The collapsed trust boundary is: a few more tags (`u`, `s`, the table family, `colgroup`/`col`) + a `class` attribute restricted to an enumerated set + enumerated `target`/`rel` + `colspan`/`rowspan` table-cell attributes. (`colwidth` is NOT allowlisted: tables are `resizable:false` so it is never emitted, and `ALLOWED_ATTR` does no value validation, so an unused unvalidated attribute only widens the surface — D1-F3.)

**Hook-scoping discipline (D1-F1).** `isomorphic-dompurify` exports a single shared DOMPurify singleton, and `DOMPurify.addHook` mutates that singleton's GLOBAL hook list — so a `class`-enumeration hook registered as an import-side-effect can detach from the sanitize call (wrong import order, tree-shaken side-effect-only registration, a future refactor that sanitizes from a path that imported DOMPurify without the hook), leaving `class` an allowlisted attribute with NO value restriction. The same singleton also sanitizes author bios with V1 `STRICT_CONFIG` (§7), so a globally-registered hook would also cross two configs. **Discipline (chosen, stated in ADR-009 §5.2):** the body sanitizer is ONE function that registers the `uponSanitizeAttribute` hook, calls `sanitize`, and `removeHook`s in the same call — `add → sanitize → remove` — so `class`/`target`/`rel` enumeration can never detach from the body render path and never leaks onto the bio path. (`isomorphic-dompurify` v2 does not expose a reliable dedicated-instance/`createDOMPurify` API on the singleton, so the add/sanitize/remove wrapper is the robust form rather than a second instance.) The Phase-1 sanitizer matrix MUST exercise the PUBLIC `renderPostBody` entry point (not a test that pre-registers the hook itself), so a missing/disordered registration fails CI.

```javascript
// renderBodyHtml(html): the SINGLE body-sanitize entry point.
// add → sanitize → remove, so the class/target/rel enumeration cannot detach (D1-F1).
function renderBodyHtml(html) {
  DOMPurify.addHook('uponSanitizeAttribute', enumerateBodyAttrs); // see hook below
  try {
    return DOMPurify.sanitize(html, STRICT_CONFIG_V2);
  } finally {
    DOMPurify.removeHook('uponSanitizeAttribute'); // bio/STRICT_CONFIG path stays hook-free
  }
}

// STRICT_CONFIG_V2 (BASELINE V1 + bounded DELTA), used at every render
const STRICT_CONFIG_V2 = {
  ALLOWED_TAGS: [
    // V1 baseline (the live config at blog-content.ts:396-424 — already includes
    // the table family, del, AND br):
    'h2','h3','h4','h5','h6','p','a','ul','ol','li','strong','em','b','i',
    'blockquote','code','pre','img','hr','br',
    'table','thead','tbody','tr','th','td','del',
    // V2 delta:
    'u',                 // underline (now first-class)
    's',                 // strike (TipTap v3 normalizes <del>/<strike> to <s>)
    'colgroup','col',    // table column groups (TipTap v3 emits these)
  ],
  ALLOWED_ATTR: [
    'href','src','alt','title',     // V1 baseline
    'target','rel',                 // Link extension defaults (enumerated by hook below)
    'class',                        // CodeBlock language-* + text-align classes (enumerated by hook below)
    'colspan','rowspan',            // table cell attributes
    // NOTE: 'colwidth' is DELIBERATELY ABSENT — tables are resizable:false so it is never
    //   emitted, and ALLOWED_ATTR does NO numeric validation; keeping an unused, unvalidated
    //   attribute only widened the surface (D1-F3). Drop it.
    // NOTE: 'style' is DELIBERATELY ABSENT — it stays banned (class-based text-align; resizable:false tables).
  ],
  ALLOW_DATA_ATTR: false,
  ALLOW_ARIA_ATTR: false,
  ALLOWED_URI_REGEXP: /^(?:https:|mailto:|tel:|\/(?![/\\]))/i, // UNCHANGED — NOT https-only (R3-F1)
  // no `id`, fragments stripped — V1 properties unchanged
};

// enumerateBodyAttrs — registered ONLY for the body render via renderBodyHtml's
// add/sanitize/remove wrapper above (D1-F1); never a global import-side-effect.
// Enumerate the class allowlist (drop the attr if no allowed token matches):
function enumerateBodyAttrs(node, e) {
  if (e.attrName === 'class') {
    const allowed = new Set([
      // CodeBlock language hints (fixed languageClassPrefix 'language-'):
      'language-js','language-ts','language-python','language-css','language-html',
      'language-sql','language-json','language-xml','language-bash','language-sh',
      // TextAlign as classes (see 5.3): exactly four
      'text-left','text-center','text-right','text-justify',
    ]);
    const kept = (e.attrValue || '').split(/\s+/).filter((c) => allowed.has(c));
    if (kept.length) e.attrValue = kept.join(' '); else e.keepAttr = false;
  }
  if (e.attrName === 'rel') {
    const allowed = new Set(['noopener','noreferrer','nofollow']);
    const kept = (e.attrValue || '').split(/\s+/).filter((r) => allowed.has(r));
    if (kept.length) e.attrValue = kept.join(' '); else e.keepAttr = false;
  }
  if (e.attrName === 'target' && e.attrValue !== '_blank' && e.attrValue !== '_self') e.keepAttr = false;
}
```

### 5.3 Class-based text-align; `resizable:false` tables — how `style` stays banned

Recon flagged that TipTap's built-in `TextAlign` emits inline `style="text-align:…"` and parses back from `element.style.textAlign`, so a class-based result requires a custom `TextAlign.extend()` overriding **both** `renderHTML` (emit `class="text-left|center|right|justify"`) **and** `parseHTML` (read that class) for a clean round-trip into the editor. That is harder, not impossible — and it is exactly the "correct" path the owner asked for. **Decision: ship the class-based custom TextAlign so the `style` attribute is never allowed.** Tables are configured `resizable: false` to eliminate the `colwidth`/`min-width` inline-style emission; **`colwidth` is therefore NOT allowlisted** (D1-F3 — it is never emitted under `resizable:false`, `ALLOWED_ATTR` does no numeric validation, and TipTap's `colwidth` is in fact a comma-list not a single number, so keeping it would be an unused, unvalidated, mis-described attribute) and no inline `min-width` style is produced. *(Recon's alternative — un-banning `style` bounded to `text-align`/`min-width` via a value-enumeration hook — is recorded as the fallback ONLY if the custom TextAlign proves genuinely unworkable, and per the owner non-negotiable the security critic must explicitly accept any style-path before it ships; flagged in §13/§16.)*

### 5.4 One-time markdown→HTML conversion of the 6 live posts (verified, late, rollback-able)

A single migration (the Phase-1 PR5 seed slot, migration `016`-style precedent) converts each live post's markdown `data.body` to HTML by running it through the EXISTING `marked` renderer → `DOMPurify.sanitize(STRICT_CONFIG_V2)` → storing the result as the new HTML `data.body`.

**Gate = rendered-output equivalence (mechanically defined — D1-F6).** For each post, the public `.blog-body` render of the stored converted HTML is compared to the pre-conversion markdown render. **The default is BYTE-EQUALITY.** Before comparing, the gate applies to BOTH sides EXACTLY this ENUMERATED, bounded normalization allowlist — nothing else:
  1. trim a single trailing newline;
  2. collapse runs of insignificant inter-tag whitespace (whitespace that is purely between tags, e.g. `>   <` → `><`);
  3. normalize self-closing void-element syntax (`<hr>` ⇄ `<hr/>`, `<br>` ⇄ `<br/>`).
Any difference OUTSIDE this list FAILS the gate. The list MUST NOT include dropping or adding any element or text (in particular it must never "normalize away" a `<br>` — see below), so it cannot launder content loss. Each normalization entry that is actually exercised requires a one-line justification in the PR5 migration doc; "documented-normalization-equal" means exactly "byte-equal after applying ONLY these three rules," not an open-ended escape hatch.

**`<br>` must round-trip (D1-F5).** `marked` with `gfm:true` (the exact config in `renderPostBody` and in this conversion path) emits `<br>` for hard line breaks (two trailing spaces / backslash-newline), and `br` is in the V1-baseline `ALLOWED_TAGS` (blog-content.ts:416) and stays in `STRICT_CONFIG_V2`, so any of the 6 posts with a hard break converts to HTML containing `<br>` and renders identically. A `<br>`-bearing fixture is included in BOTH the conversion equivalence fixtures and the Phase-1 sanitizer matrix so a dropped `<br>` (which would have silently broken the gate under the old config that omitted `br`) cannot recur.

**Rollback is mechanically real (D1-F4) — code-revert ALONE is NOT a rollback.** The 6 bodies live in Neon `data.body`, not the repo; the conversion overwrites that value in place, so reverting only the code (flipping `renderPostBody` back to markdown→`DOMPurify(STRICT_CONFIG_V1)`) leaves converted HTML in the DB and the V1 renderer would run `marked` over HTML and serve literal `<h2>…</h2>`/`<strong>…</strong>` tags as text — the exact render-first failure mode this section forbids. A real rollback must RE-WRITE markdown into `data.body`. Therefore the conversion migration FIRST snapshots each row's current live markdown into a transient per-row backup (a `data.bodyMarkdownBackup` key on the row, keyed by `slug`+`updated_at`) BEFORE overwriting `data.body`; **rollback = a documented reverse migration that copies the backup back into `data.body`, run TOGETHER with the code-revert of `renderPostBody`.** This transient backup is a deliberate, scoped reversal of §2.1's "no sidecar key" decision FOR THE CONVERSION'S DURATION only (it is removed in a follow-up once the conversion is ratified). **Git history (migration 015) is at best a SECONDARY, STALE source** — its `ON CONFLICT (type,slug) DO NOTHING` was applied manually at rollout and never clobbers owner-edited rows, so any post edited via `/admin/blog` after import has diverged from migration 015; a git-based restore would serve stale/wrong content and silently violate invariant #1. The pre-migration live-row snapshot, not git, is the authoritative rollback source.

**ATOMIC CUTOVER — the public render switch and the data conversion ship in the SAME PR/deploy (sequencing is load-bearing).** `renderPostBody` (`blog-content.ts:364`) serves the PUBLIC 6 posts and is NOT admin-gated, and every merge to main auto-deploys with no per-PR owner checkpoint. So the public `renderPostBody` MUST keep its markdown→`DOMPurify(STRICT_CONFIG_V1)` behavior for the 6 live (still-markdown) rows until the moment the data is converted — flipping the public render to expect HTML BEFORE the rows are HTML would serve `## Heading` and dead links as literal text on a live deploy (violating invariant #1 and "leaves live blog healthy"). Therefore: the editor, `STRICT_CONFIG_V2`, the HTML-aware alt gate, and the equivalence harness are built and tested in earlier PRs while the public render stays on V1; the FINAL Phase-1 PR **converts the 6 rows AND flips `renderPostBody` to stored-HTML→`DOMPurify(STRICT_CONFIG_V2)` in one deploy** (equivalently: a transitional markdown fallback in `renderPostBody`, removed once conversion completes). Conversion-first is also safe (marked's output is simple tags — headings, paragraphs, lists, links, `<strong>`/`<em>`, `<code>`/`<pre>`, `<img>`, `<hr>`, AND `<br>` — all within the V2 allowlist now that `br` is confirmed present in `STRICT_CONFIG_V2.ALLOWED_TAGS` (D1-F5), and double-sanitization is idempotent), but render-first is forbidden.

### 5.5 Faithful preview, hydration, and the HTML-aware alt gate

- **Faithful preview** re-renders through the real `.blog-body` pipeline (`renderPostBody` over stored HTML), NOT the editor canvas and NOT `.prose` (`@tailwindcss/typography` is not installed; `.prose` is unstyled here — R3-F11).
- **Hydration on load** uses `setContent(html, { parseOptions: { preserveWhitespace: 'full' } })`; on save the editor's `getHTML()` is sanitized (write-time hygiene) then persisted, and re-sanitized at render.
- **HTML-aware alt gate (R2-F4, NOW ACTIVE — see §1 invariant #4).** `collectBodyImageAlts`'s markdown-token walk does not see `<img>` tags, which HTML bodies now contain. Phase 1 replaces/augments it with a DOM-walk over the sanitized HTML's `<img>` nodes (missing/empty `alt` flagged) so the converted 6 posts and all new TipTap/AI body images are gated. This lands BEFORE the editor is adopted.
- **AI output format (reviser decision).** AI body output is **constrained HTML, sanitized at insertion** (Recon 2 recommendation): it eliminates a markdown→HTML round-trip on every generation and keeps WYSIWYG fidelity end-to-end model→storage→render. It has **no privileged write path** — it flows through `validateBlogData` + the SAME `DOMPurify(STRICT_CONFIG_V2)` as human content, and is re-sanitized at render like everything else (§6/§7). *(If the model proves unreliable at constrained HTML, the documented alternative is markdown emitted by the model and converted at insertion via the conversion renderer — same sanitizer boundary; recorded for ADR-010.)*

## 6. AI Writing & Voice System (Phase 7) — ADR-010 (NEW, authored in Phase 7)

The AI subsystem is the LAST phase, key-optional by design, with its own ADR-010. Full security/cost/latency criteria are enumerated in §11 Phase 7; this is the architecture summary.

- **Key-optional.** The Anthropic key is stored in a NEW `admin_settings` table (`is_sensitive=true`), encrypted at rest by a NEW `crypto.ts` (AES-256-GCM, per-encryption random IV + auth tag, fail-closed). Decrypted only at request time in memory. `isAiConfigured` returns a boolean only — never key material. When no key is configured, every AI route 404s and every AI affordance is hidden.
- **Async-by-default for LONG actions (owner override 2026-06-07: "Let's not worry about synchronous drafting").** Long-running generation — `draft` and voice generation — runs as a **background job by default**: the POST validates, counts spend at enqueue (below), writes an `ai_jobs` row `status='pending'`, returns `202` + `job_id`; a `-background` Netlify function processes the job (calls Claude, ~15-min cap) and **persists its result durably into the `ai_jobs` row** (`ai_jobs.status='completed'` + the generated body written to `ai_jobs.result`). **The session-authed client then performs the `data.body` write** — it polls a GET job endpoint, and on `completed` inserts `result` through the NORMAL authed save path (`checkAdminAuth` + `validateBlogData` + `DOMPurify(STRICT_CONFIG_V2)` + `author_email = session.userEmail`). **The worker NEVER writes `content.data.body` directly** — it has no session and no `locals`, so a direct write would be a net-new non-session privileged path with unspecified attribution; pinning the body write on the authed client preserves "no privileged write path" verbatim (D1-F9). *(The owner's "auto-save or something" is satisfied by the durable persistence of the result in `ai_jobs.result`; whether to additionally auto-insert it into `data.body` without an explicit owner gesture, vs. surfacing it for one-click accept, is the localStorage-autosave-adjacent interpretation flagged for owner review in §13/§16 — recorded, not silently built.)*
  - **At-least-once execution + idempotent claim (D1-F8).** Netlify on-demand background functions run on Lambda async invocation, which is AT-LEAST-ONCE: a failed invocation is auto-retried (~1 min, then ~2 min — up to 3 invocations per single enqueue). Because the breaker increments exactly ONCE at enqueue, a job that fails AFTER the Claude call but before the result persists would otherwise be re-invoked and re-bill Claude UNCOUNTED — up to 3× the per-action cost from one enqueue, and a fail-after-Claude burst could blow past the daily cap the breaker enforces. The worker therefore MUST atomically CLAIM the job before any Claude call — `UPDATE ai_jobs SET status='processing', attempts=attempts+1 WHERE id=$1 AND status='pending' RETURNING ...` — and **bail with NO Claude call if zero rows are claimed** (the job is already `processing`/`completed`/`failed`), mirroring the repo's existing `claimDueJobs` `FOR UPDATE SKIP LOCKED` idempotency that the on-demand PUSH model otherwise loses. This makes a retry of an already-processed job a no-op, so the enqueue-time count bounds the ACTUAL Claude-call count, not just the enqueue count. The `ai_jobs` table + background function + poll endpoint + polling UI are DEFAULT Phase-7 scope (no longer opt-in-only).
  - **`ai_jobs` schema (D1-F9, NEW — added to docs/specs + the Phase-7 migration list).** `CREATE TABLE ai_jobs ( id uuid PRIMARY KEY DEFAULT gen_random_uuid(), kind text NOT NULL CHECK (kind IN ('draft','voice')), status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','processing','completed','failed')), content_id integer REFERENCES content(id), target_slug text NOT NULL, admin_email text NOT NULL, params jsonb NOT NULL, result text, error text, attempts integer NOT NULL DEFAULT 0, created_at timestamptz NOT NULL DEFAULT now(), updated_at timestamptz NOT NULL DEFAULT now() )`. `target_slug`/`content_id` link the job to the draft; `admin_email` is the enqueuing admin captured at enqueue (authz: the enqueuer must be authorized to edit that post — checked at enqueue, and re-checked by the authed client at the `data.body` insert since the client write is the only path that touches `content`). The worker writes only `status`/`result`/`error`/`attempts`/`updated_at` on the `ai_jobs` row; it never touches `content`.
  - **Sync/async split + model defaults.** Short actions (inline rewrites, excerpt, headline, SEO field) stay **synchronous** — they fit the function timeout comfortably. **Model defaults UNCHANGED:** Sonnet 4.6 is the default model, Opus 4.8 is opt-in; async removes the infrastructure penalty from choosing async but does NOT promote Opus to default (the Opus-vs-Sonnet cost/quality choice stays an owner decision). The synchronous-timeout constraint no longer shapes the design, so the R4-F6 "26s tier gates the synchronous draft" hard gate is RETIRED for `draft` (which is async); the tier confirmation downgrades to informational for the short synchronous actions. **Per-action `max_tokens` ceilings** (inline ~512, excerpt/headline ~256, draft 1500-2000) remain the per-action hard backstop on output-rate billing AND bound a single background-job invocation under the 15-min cap.
- **Enqueue-time spend counting (async abuse coverage).** The daily spend breaker and per-window rate limiter EXPLICITLY cover the background-job path: spend is **counted at ENQUEUE, not at completion** — a queue burst must trip the breaker BEFORE fan-out, so the breaker check-and-increment happens when the `202` is returned (rejecting the enqueue), not when the background function later finishes. The rate limiter likewise gates the enqueue POST and the corpus-ingestion route. (This supersedes the old "the daily breaker trips only AFTER a call returns" reasoning, which held only for the synchronous design.)
- **Three modes** (per the old spec §7): (1) in-editor selection toolbar (rewrite/simplify/shorten/expand/tone — synchronous); (2) panel whole-post actions (headline, excerpt — synchronous; first draft — async background job; category/tag suggestions); (3) per-field SEO AI (synchronous). All flow through one internal service that prepends the voice config as data-delimited context, emits **constrained HTML** (the storage format), and routes through `validateBlogData` + `DOMPurify(STRICT_CONFIG_V2)` + render-time re-sanitization (no privileged write path; §5.5/§7).
- **Voice system** in `admin_settings`: reference corpus (curated seed; auto-add opt-in), plain-language Style Profile (NOT raw scores, R2-F18), anti-pattern blocklist (enforced IN-PROMPT on the single generation, NOT a second corrective call — R4-F13), structured voice instructions (keyboard-reorderable), few-shot selection.
- **Security envelope:** CSRF (fail-closed on both-signals-absent) on every AI route — synchronous AND the async-enqueue route AND the corpus-ingestion route; atomic DB-backed spend breaker + per-window rate limiter (both 429 before any Anthropic call OR outbound fetch OR job enqueue — count at enqueue, not completion); SSRF defense via app-side hardened fetch passing HTML to `extractFromHtml` (never `extract({url})`), connection-pinning vs DNS rebinding, plus a hardened-fetch contract (AbortController read timeout + STREAMING max-bytes cap + Content-Length early reject — R4-F3); SEO/OG per-field escaping + scheme validation.
- **Cost honesty:** prompt cache defaults to `ttl: '5m'` (R4-F7); per-action cost derived from `max_tokens` output + measured typical thinking, labelled a typical estimate, with the per-action MAX stated in ADR-010.

## 7. Security Posture (write/render boundary)

- **The body trust boundary under HTML storage (new statement).** Storing TipTap HTML does NOT move the trust boundary to write-time. The boundary is **render-time `DOMPurify.sanitize(STRICT_CONFIG_V2)`** on the single render path (§4/§5.1): every page render re-sanitizes stored HTML, so a config tightening or a write-path bug can never serve stored XSS. The bounded V2 delta keeps the `style` attribute BANNED — text-align is a small enumerated CLASS allowlist and tables are `resizable:false` — so the new surface is: a few more tags (`u`, `s`, table family, `colgroup`/`col`) + an enumerated `class` set + enumerated `target`/`rel` + `colspan`/`rowspan` table-cell attributes (`colwidth` NOT allowlisted, D1-F3) (§5.2). Sanitize-on-write is permitted only as extra hygiene; it is never the sole gate. AI body output is the SAME stored HTML through the SAME render-time sanitizer — no privileged path.
- **Write-validation cannot be the only gate.** The generic `/api/admin/settings` endpoint is a bypass door: ticker hrefs and author bios are therefore validated/sanitized at **RENDER time**, not only on write (R1-F2). Ticker hrefs use a dedicated LINK-href validator allowing `mailto:`/`tel:`/`https:`/site-relative (NOT `IMAGE_SCHEME_REGEX`, R3-F4). Author bios render through DOMPurify `STRICT_CONFIG`.
- **CSRF reality.** `/api/admin/settings` has NO Origin/Sec-Fetch check today — Phase 6 adds one (R2-F1). No `admin_settings` write path exists anywhere — Phase 7 BUILDS a new authenticated + CSRF + encrypt-on-write endpoint (R2-F2). The inherited `content.ts` CSRF check fails OPEN when both Origin and Sec-Fetch-Site are absent — AI spend/ingestion routes AND the async-job ENQUEUE route use a STRICTER fail-closed posture, and the spend breaker counts at enqueue so a queue burst trips the breaker before fan-out (R3-F6, async abuse coverage).
- **Status visibility hardened at storage.** Phase 2 adds `CHECK (status IN ('draft','published','scheduled','archived'))` on `content.status` (R4-F2) — defense-in-depth behind the exact-match published read filter.
- **Forgeable inputs labelled.** Phase-5 view counts are constrained to published slugs and labelled best-effort/forgeable; `page_path` is rendered only via Astro auto-escaping (R3-F3).

Mitigated by a SINGLE atomic check-and-increment `ai_usage` statement for spend (**counted at ENQUEUE for the async draft/voice path so a queue burst trips the breaker before fan-out**) PLUS a DB-backed atomic per-window request-rate limit (same pattern, `ai_rate` window) gating **Anthropic-call routes AND the corpus-ingestion outbound fetch AND the async-job enqueue route (R4-F4, async abuse coverage)**, all returning 429 before any Anthropic call or outbound fetch or job enqueue + real-Neon race verification at checkpoint (incl. an enqueue-burst race) + prompt caching (**default 5m TTL** — R4-F7) that keeps the corrected per-action estimates (incl. Opus thinking tokens R3-F8, bounded by the per-action `max_tokens` ceiling R4-F8) honest.
