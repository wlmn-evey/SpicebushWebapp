# ADR-010: AI Writing and Voice System for the Blog

**Date**: 2026-06-06 (async-default update 2026-06-07)
**Status**: Proposed

> This subsystem is unbuilt. It is the final phase of the Blog V2 work and carries one open owner question (the key-storage mode) and one hard prerequisite (written confirmation that the Netlify plan supports on-demand background functions). The status is "Proposed" rather than "Accepted" because the architecture is settled but the build is gated on owner decisions.
>
> **Owner override 2026-06-07 — async-by-default.** The owner directed: *"Let's not worry about synchronous drafting."* Long-running AI actions (full draft, voice generation) now run as a **background job by default** (`202` → poll → result), not as a synchronous call gated on the function timeout. Short actions stay synchronous. **Model defaults are UNCHANGED — Sonnet 4.6 default, Opus 4.8 opt-in:** async removes the infrastructure penalty from choosing async but does not promote Opus to default; that remains an owner cost/quality decision. The synchronous-timeout constraint no longer shapes the design, so the prior "synchronous Sonnet default / Opus async opt-in" framing and the "26s tier gates the synchronous draft" prerequisite are superseded by what follows. The spend breaker and rate limiter now count at **enqueue**, so a queued burst trips the breaker before fan-out.

## Context

The DB-backed blog (ADR-008) lets non-technical owners author posts at `/admin/blog` with no deploys. Blog V2 layers the full feature set the owner reaffirmed on 2026-06-06 — a TipTap editor (ADR-009), categories and tags, a homepage ticker, scheduled publishing, staff and virtual authors, RSS, and more. The last and largest piece is an AI writing assistant: inline rewrites and tone adjustments on selected text, AI-generated excerpts and headlines, AI-assisted SEO metadata, full draft generation, and a "voice" system that conditions all of this on the school's own writing — a corpus of representative posts, a derived style profile, an anti-pattern blocklist, and freeform voice instructions.

Three forces make this subsystem fundamentally different from every phase before it, and they are why it ships last:

- **It is the only phase with recurring external cost.** Every other feature is a one-time build against the school's own database and Netlify functions. AI features call the Anthropic API on every invocation, billed per token, indefinitely. The school pays for usage forever.
- **It is the highest security surface in the project.** It introduces a secret to store (an Anthropic API key), an owner-pasted-URL ingestion path (an SSRF and cost-blowout vector), untrusted model output flowing toward the publish pipeline (an injection vector), and a spend exposure that an unauthenticated or unthrottled endpoint could exhaust.
- **It is invisible by default.** Every AI affordance is hidden until the owner configures an API key. A school that never configures one gets exactly the blog described by Phases 1–6, fully functional, with zero AI code reachable. The subsystem therefore adds the most risk and external dependency for the least baseline value, and deferring it until the rest of the blog is healthy is the correct ordering.

The site has no precedent for any of the primitives this needs. There is no encryption helper anywhere in the codebase; the one comparable feature (the Gemini-backed SEO suggester at `src/pages/api/admin/seo/gemini-suggest.ts`) reads a plaintext `GEMINI_API_KEY` from an environment variable, performs an unbounded `await response.text()` on an owner-supplied URL fetch, and is the pattern to *exceed*, not copy. There is no `admin_settings` write path and no `crypto.ts`. There is no DB-backed rate limiter or spend breaker. All of these are net-new and must be built and tested as security-critical surfaces.

## Decision

Build the AI writing/voice subsystem as the final, independently-shippable phase of Blog V2, key-optional by design, with the architecture below. Nothing in this subsystem is reachable by the public; every endpoint is behind the existing magic-link admin auth plus CSRF, and every affordance is gated on a configured key.

**Key-optional gating.** A single boolean, derived server-side, governs the whole subsystem: AI is "configured" only when a decryptable Anthropic API key is present in admin settings. When it is not, the AI routes return 404 and the editor renders no AI controls. The boolean is the only thing any read path exposes — no endpoint ever returns key material, and the gate fails closed: if the key cannot be decrypted (for any reason, including a master-key mistake), the subsystem reports "not configured" and disables itself rather than erroring or leaking.

**Encrypted key at rest in a new `admin_settings` table.** The Anthropic key is entered through the admin UI and stored encrypted with AES-256-GCM — a fresh random 12-byte IV per encryption, the GCM authentication tag stored alongside the ciphertext, and decryption that fails closed on any tag mismatch or bad master key. The AES master key lives in a Netlify environment variable; DB encryption protects the working key at rest, not the root secret. This requires building a new `crypto.ts` helper and a new authenticated, CSRF-protected, encrypt-on-write `admin_settings` endpoint — neither exists today. (The alternative, a plaintext env var with no admin UI, is a live owner question; see below.)

**Execution model and tiers.** Short actions (inline rewrites, tone changes, excerpt, headline, SEO fields) run **synchronously** and fit the function timeout comfortably. Long actions (full draft, voice generation) run as a **background job by default** (owner override 2026-06-07): the POST validates, counts spend at enqueue, writes an `ai_jobs` row `status='pending'`, and returns `202` + a `job_id`; an on-demand `-background` Netlify function (15-minute cap) calls Claude and **persists its result durably into the `ai_jobs` row** (`ai_jobs.status='completed'` with the generated body written to `ai_jobs.result`). The session-authed client then polls a job endpoint and, on `completed`, inserts the result into `data.body` through the **normal authed save path** (`checkAdminAuth` + `validateBlogData` + sanitizer + `author_email = session.userEmail`). The worker never writes `content` directly — it has no session and no `locals`, so a direct `content.data.body` write would be a net-new non-session privileged path with unspecified attribution; keeping the body write on the authed client preserves "no privileged write path" (see Injection defenses below). **At-least-once execution:** on-demand background functions run on Lambda async invocation (at-least-once, up to ~3 invocations per enqueue on failure), so the worker MUST atomically claim the job (`UPDATE ai_jobs SET status='processing', attempts=attempts+1 WHERE id=$1 AND status='pending' RETURNING ...`) and bail with no Claude call if zero rows are claimed — so a retry of an already-processed job is a no-op and the enqueue-time spend count bounds the ACTUAL Claude-call count, not just the enqueue count. A worker invocation that errors sets `status='failed'` (never stuck `pending`); a max-age detector surfaces a never-invoked/crashed job so the client does not poll forever. The `ai_jobs` table (`id`, `kind`, `status` ∈ {pending, processing, completed, failed}, `content_id`/`target_slug`/`admin_email` linkage, `params`, `result`, `error`, `attempts`, timestamps), background function, poll endpoint, and polling UI are default scope — they no longer hinge on a model choice; the schema and migration are specified in the implementation plan (§6) and `docs/specs/blog.md`.

The default generation model is **Claude Sonnet 4.6** (`claude-sonnet-4-6`); inline rewrites and tone changes may use **Claude Haiku 4.5** (`claude-haiku-4-5`) for latency and cost. The most capable model, **Claude Opus 4.8** (`claude-opus-4-8`), is an explicit owner opt-in for the best drafts. With async as the default execution model, the Opus opt-in is a **model swap plus a cost change, not a net-new subsystem** — the background-job path exists regardless of model. The Opus cost delta (its higher token price plus billed adaptive-thinking tokens, ~2× visible output at high effort) is surfaced; the choice remains the owner's.

Cost is bounded and surfaced. Every action carries an explicit `max_tokens` ceiling (inline rewrites ~512, excerpt/headline ~256, full draft 1500–2000), which is the only per-action hard token backstop on spend — adaptive thinking on Opus has no fixed token budget. The `max_tokens` ceiling also bounds a single background-job invocation well inside the 15-minute cap. Pricing anchors the surfaced figures: Sonnet 4.6 is $3 / $15 per million input/output tokens, Haiku 4.5 $1 / $5, Opus 4.8 $5 / $25. The per-action cost shown in the UI is labelled a *typical estimate*; the implementation plan records the per-action *maximum* (max_tokens output plus, on the Opus path, the maximum observed adaptive-thinking tokens, which bill at the output rate). Under the default Sonnet model, total spend for a small school's bursty authoring is expected to be low single-digit dollars per month. Prompt caching of the stable voice/corpus prefix uses the default 5-minute TTL (a 1.25× write premium, break-even at two reads), not the 1-hour TTL (2× write, break-even at three reads) — a sparse single-author workload rarely fires three AI calls against an identical prefix within an hour, so 1-hour caching is a net cost *increase* here. Caching is dropped entirely below the model's minimum cacheable prefix (4096 tokens for Opus, 2048 for Sonnet 4.6), below which a `cache_control` marker is a pure write premium that never pays back.

**Voice-corpus system.** The voice subsystem — the corpus of representative posts, the derived style profile, the anti-pattern blocklist, and freeform voice instructions — is stored in `admin_settings`, not in the public `settings` table, so it never enters a public read path or the public settings export. The corpus ships with a small curated seed; the owner may add posts or ingest from a pasted URL. Anti-pattern enforcement is *in-prompt*: the blocklist (e.g. "delve", "tapestry") is injected into the instruction envelope of the single generation call, not enforced by a second corrective call, so the surfaced per-action cost and the synchronous-latency budget stay honest. The style profile is rendered to the owner in plain language, not as raw numeric scores.

**Injection and SSRF defenses.** Corpus and voice text are placed in the *data* portion of every prompt, never the instruction slot, and are delimited so a hostile corpus post cannot rewrite the model's instructions. Model output has no privileged path: anything the model produces for a post body flows through the same `validateBlogData` and sanitizer pipeline as human-authored content (ADR-008, ADR-009), and SEO/OG fields get per-field escaping and scheme validation — there is no direct DB write from a model response. This holds for the async path too: the background worker persists generated text only to `ai_jobs.result`, and the session-authed client performs the `content.data.body` write through the normal authed save path, so a model response never reaches `content` except through the human-content gate. The owner-pasted-URL corpus-ingestion fetch is hardened beyond the `gemini-suggest.ts` precedent: an SSRF allowlist that rejects private IPs, non-HTTPS targets, redirects to private addresses, and DNS-rebinding (validation lookup public, connect-time private), passing the fetched HTML to the extractor rather than letting the extractor fetch; plus an `AbortController` read timeout, a streaming maximum-response-bytes cap that aborts mid-stream rather than buffering an unbounded body, and an early reject on an oversized `Content-Length`. This closes both *where* the fetch connects and *how long it runs / how much it reads* — the cost-blowout and memory-exhaustion vectors on a serverless function.

**Abuse limits — enqueue-time counting.** Two DB-backed, atomic, single-statement controls protect spend: a daily spend breaker (a single check-and-increment against an `ai_usage` row, decision taken from the `RETURNING` value, no read-then-write across an `await`) and a per-window request-rate limiter using the same pattern. Both return `429` *before* any Anthropic call is made, *before* any owner-triggered outbound fetch, and — critically for the async path — **before any background-job enqueue: spend is counted at enqueue, not at completion, so a queue burst trips the breaker before fan-out** rather than after the jobs have already run. The rate limiter gates the Anthropic-call routes, the corpus-ingestion route (which makes no Anthropic call but an outbound fetch), and the async-job enqueue route, so a same-origin burst cannot fan out into many concurrent fetches or queued jobs. An in-memory limiter would be unenforceable across serverless instances and is forbidden.

**CSRF posture.** Every AI mutation, spend, ingestion, and async-job-enqueue route requires admin auth and rejects a cross-site POST. The spend, ingestion, and enqueue routes additionally fail closed when both the `Origin` and `Sec-Fetch-Site` signals are absent, rather than inheriting the generic admin endpoint's fail-open behavior in that case.

## Consequences

- **Easier**: A school that wants AI help gets it conditioned on its own voice, self-served from the admin UI with no developer involvement and no deploy — consistent with the rest of the blog's authoring model.
- **Easier**: A school that does not want AI gets a fully functional blog with the entire subsystem dormant and unreachable. The key-optional gate means "no key" is a complete, supported, zero-cost configuration, not a degraded one.
- **Easier**: Cost is visible and bounded at the point of use — per-action estimates in the UI, a hard `max_tokens` ceiling per action, a daily spend breaker counted at enqueue, and a rate limiter — rather than discovered on a monthly bill.
- **Easier**: Async-by-default removes the synchronous wall-clock timeout as a design constraint on long actions. A full draft is not racing a 10s/26s function limit; it runs in a background function (15-minute cap, at-least-once with an idempotent claim) and persists its result durably to `ai_jobs.result` for the authed client to insert. The model choice (Sonnet vs Opus) becomes a pure cost/quality decision rather than also a latency/infrastructure decision.
- **Harder**: The school pays a recurring, usage-based external bill for as long as AI is enabled. The default Sonnet model is expected to be low single-digit dollars per month for this workload, but the Opus opt-in is materially more expensive (higher token price plus billed adaptive-thinking tokens), and any future second-pass generation would roughly double per-action cost.
- **Harder**: This is the project's largest net-new security surface, and almost none of it has prior art in the codebase: custom AES-256-GCM crypto, a new encrypt-on-write `admin_settings` endpoint, an SSRF allowlist with rebinding defense, a hardened streaming fetch, a DB-backed spend breaker, a DB-backed rate limiter, and an on-demand background-job subsystem (`ai_jobs` + `-background` function + poll endpoint/UI) for which the repo has no precedent (only scheduled-cron drains). The background subsystem in particular must treat the platform's AT-LEAST-ONCE invocation as a first-class assumption: an idempotent atomic claim (no Claude call if the job is not still `pending`) so a retry never re-bills the enqueue-counted spend, fail-closed (`status='failed'`, never stuck `pending`) on a worker error, and a max-age stuck-job detector so a never-invoked job is observable rather than an infinite client poll. Each must be built and maintained as security-critical, not as a convenience feature.
- **Harder**: There are two key-rotation modes and they are not interchangeable. Rotating the Anthropic key is simple — re-enter it in the admin UI, and it is re-encrypted on write under the current master key. Rotating the AES master key requires decrypting every stored sensitive blob with the old key and re-encrypting with the new key *before* the environment variable is swapped. Swapping the master key without re-encrypting silently fails closed: GCM authentication fails, the gate reports "not configured", and the entire AI subsystem disappears — operationally indistinguishable from a rotation mistake. This footgun must be loud in the runbook because the system itself cannot make it loud.
- **Trade-off**: Fail-closed-as-not-configured is the right security posture — a key that cannot be decrypted must never be used — but it is operationally confusing, because a genuine misconfiguration and a deliberate "no key" state look identical to the operator. We accept this in exchange for never operating on a key we cannot prove is intact.
- **Trade-off**: Defaulting to Sonnet 4.6 (and Haiku for inline actions) rather than the most capable model trades some draft quality for lower cost. With async as the default execution model, this is now a pure cost/quality choice — the background-job subsystem exists regardless — so Opus 4.8 remains an explicit opt-in for higher spend (and higher quality), not a trigger for net-new infrastructure.
- **Trade-off**: Storing the working key encrypted in the database protects it at rest but does not protect the AES master key, which still lives in a Netlify environment variable. DB encryption narrows the exposure (a database dump alone does not yield a usable key) without eliminating the root-secret dependency.

## Open Questions and Prerequisites

- **Key storage mode (SETTLED — owner decision 2026-06-07).** The owner chose the encrypted-in-`admin_settings` design — *"let's just use the database we're paying for for that"* — over the plaintext-env-var alternative. The Anthropic key is entered through the admin UI and stored AES-256-GCM-encrypted in the Neon database; `crypto.ts`, the key-entry UI, and the new CSRF'd encrypt-on-write `admin_settings` endpoint are confirmed Phase-7 deliverables. The env-var alternative (smaller diff, but redeploy-to-rotate and no in-app key management) is rejected. The master-key-rotation footgun documented under Consequences applies and must be loud in the runbook.
- **AI execution model (SETTLED — owner override 2026-06-07).** Long actions are async-by-default (background job, 202 → poll → result persisted durably to `ai_jobs.result`, then inserted into `data.body` by the session-authed client — the worker never writes `content` directly); short actions synchronous. No remaining owner choice on sync-vs-async.
- **AI model (owner decision — cost/quality only).** The default model is Sonnet 4.6 (Haiku for inline). Opus 4.8 is an explicit opt-in for higher quality at higher cost (token price plus billed adaptive-thinking tokens). Because the execution model is async regardless, the Opus opt-in is now purely a cost/quality decision, not an infrastructure one. The plan proceeds on the Sonnet default unless the owner opts in.
- **Netlify on-demand background functions (hard prerequisite).** The async-default design needs on-demand background functions (`-background` suffix, 15-minute cap, 202 response). The repo's only async precedent is scheduled-cron drains, so availability on the site's plan must be confirmed *in writing before this phase's implementation begins*. The synchronous 10s/26s tier is now informational — it bears only on the short synchronous actions, which fit either tier — and no longer gates the draft action.
- **localStorage autosave (interpretation, recorded for owner review — not built).** The owner's "auto-save or something" is interpreted as the background job durably persisting its result to `ai_jobs.result`, which the session-authed client then inserts into `data.body` through the normal save path (the worker never writes `content` directly). Whether the client AUTO-inserts that result on `completed` vs. surfaces it for one-click accept is the autosave-adjacent question; client-side localStorage autosave stays on the V1 OUT list (deliberately cut); reviving either auto-behavior is a separate owner decision. Recorded here, not silently built.

See ADR-008 (DB-backed blog), ADR-009 (storage and editor), `docs/specs/blog.md` (AI/voice spec), and the Blog V2 implementation plan for the per-phase build sequence, test taxonomy, and the operational runbook covering key rotation, the spend breaker, and the rate limiter.
