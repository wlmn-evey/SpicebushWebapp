# ADR-010: AI Writing and Voice System for the Blog

**Date**: 2026-06-06
**Status**: Proposed

> This subsystem is unbuilt. It is the final phase of the Blog V2 work and carries two open owner questions (the key-storage mode and the AI generation tier) and one hard prerequisite (written confirmation of the Netlify plan's synchronous-function timeout). Those are spelled out under Consequences and Open Questions below; the status is "Proposed" rather than "Accepted" because the architecture is settled but the build is gated on owner decisions.

## Context

The DB-backed blog (ADR-008) lets non-technical owners author posts at `/admin/blog` with no deploys. Blog V2 layers the full feature set the owner reaffirmed on 2026-06-06 — a TipTap editor (ADR-009), categories and tags, a homepage ticker, scheduled publishing, staff and virtual authors, RSS, and more. The last and largest piece is an AI writing assistant: inline rewrites and tone adjustments on selected text, AI-generated excerpts and headlines, AI-assisted SEO metadata, full draft generation, and a "voice" system that conditions all of this on the school's own writing — a corpus of representative posts, a derived style profile, an anti-pattern blocklist, and freeform voice instructions.

Three forces make this subsystem fundamentally different from every phase before it, and they are why it ships last:

- **It is the only phase with recurring external cost.** Every other feature is a one-time build against the school's own database and Netlify functions. AI features call the Anthropic API on every invocation, billed per token, indefinitely. The school pays for usage forever.
- **It is the highest security surface in the project.** It introduces a secret to store (an Anthropic API key), an owner-pasted-URL ingestion path (an SSRF and cost-blowout vector), untrusted model output flowing toward the publish pipeline (an injection vector), and a spend exposure that an unauthenticated or unthrottled endpoint could exhaust.
- **It is invisible by default.** Every AI affordance is hidden until the owner configures an API key. A school that never configures one gets exactly the blog described by Phases 1–6, fully functional, with zero AI code reachable. The subsystem therefore adds the most risk and external dependency for the least baseline value, and deferring it until the rest of the blog is healthy is the correct ordering.

The site has no precedent for any of the primitives this needs. There is no encryption helper anywhere in the codebase; the one comparable feature (the Gemini-backed SEO suggester at `src/pages/api/admin/seo/gemini-suggest.ts`) reads a plaintext `GEMINI_API_KEY` from an environment variable, performs an unbounded `await response.text()` on an owner-supplied URL fetch, and is the pattern to *exceed*, not copy. There is no `admin_settings` write path and no `crypto.ts`. There is no DB-backed rate limiter or spend breaker. All of these are net-new and must be built and tested as security-critical surfaces.

## Decision

Build the AI writing/voice subsystem as the final, independently-shippable phase of Blog V2, key-optional by design, with the architecture below. Nothing in this subsystem is reachable by the public; every endpoint is behind the existing magic-link admin auth plus CSRF, and every affordance is gated on a configured key.

**Key-optional gating.** A single boolean, derived server-side, governs the whole subsystem: AI is "configured" only when a decryptable Anthropic API key is present in admin settings. When it is not, the AI routes return 404 and the editor renders no AI controls. The boolean is the only thing any read path exposes — no endpoint ever returns key material, and the gate fails closed: if the key cannot be decrypted (for any reason, including a master-key mistake), the subsystem reports "not configured" and disables itself rather than erroring or leaking.

**Encrypted key at rest in a new `admin_settings` table.** The Anthropic key is entered through the admin UI and stored encrypted with AES-256-GCM — a fresh random 12-byte IV per encryption, the GCM authentication tag stored alongside the ciphertext, and decryption that fails closed on any tag mismatch or bad master key. The AES master key lives in a Netlify environment variable; DB encryption protects the working key at rest, not the root secret. This requires building a new `crypto.ts` helper and a new authenticated, CSRF-protected, encrypt-on-write `admin_settings` endpoint — neither exists today. (The alternative, a plaintext env var with no admin UI, is a live owner question; see below.)

**Model tiers and cost posture.** The default generation model is **Claude Sonnet 4.6** (`claude-sonnet-4-6`), run synchronously. This is a deliberate departure from defaulting to the most capable model: a Netlify serverless function has a hard wall-clock timeout (10s by default, 26s only on higher plan tiers), and a synchronous Sonnet call fits that budget for the short actions while costing meaningfully less. Inline rewrites and tone changes may use **Claude Haiku 4.5** (`claude-haiku-4-5`) for latency. The most capable model, **Claude Opus 4.8** (`claude-opus-4-8`), is an explicit owner opt-in for the best drafts; because Opus at high effort can exceed the synchronous timeout, choosing it also turns the long-running actions (draft and voice generation) into a net-new background-job subsystem (a `202`/poll pattern with an `ai_jobs` table and polling UI) that is built *only* under the opt-in.

Cost is bounded and surfaced. Every action carries an explicit `max_tokens` ceiling (inline rewrites ~512, excerpt/headline ~256, full draft 1500–2000), which is the only per-action hard backstop on spend — adaptive thinking on Opus has no fixed token budget, and the daily spend breaker only trips *after* a call returns. Pricing anchors the surfaced figures: Sonnet 4.6 is $3 / $15 per million input/output tokens, Haiku 4.5 $1 / $5, Opus 4.8 $5 / $25. The per-action cost shown in the UI is labelled a *typical estimate*; the implementation plan records the per-action *maximum* (max_tokens output plus, on the Opus path, the maximum observed adaptive-thinking tokens, which bill at the output rate). Under the default synchronous-Sonnet path, total spend for a small school's bursty authoring is expected to be low single-digit dollars per month. Prompt caching of the stable voice/corpus prefix uses the default 5-minute TTL (a 1.25× write premium, break-even at two reads), not the 1-hour TTL (2× write, break-even at three reads) — a sparse single-author workload rarely fires three AI calls against an identical prefix within an hour, so 1-hour caching is a net cost *increase* here. Caching is dropped entirely below the model's minimum cacheable prefix (4096 tokens for Opus, 2048 for Sonnet 4.6), below which a `cache_control` marker is a pure write premium that never pays back.

**Voice-corpus system.** The voice subsystem — the corpus of representative posts, the derived style profile, the anti-pattern blocklist, and freeform voice instructions — is stored in `admin_settings`, not in the public `settings` table, so it never enters a public read path or the public settings export. The corpus ships with a small curated seed; the owner may add posts or ingest from a pasted URL. Anti-pattern enforcement is *in-prompt*: the blocklist (e.g. "delve", "tapestry") is injected into the instruction envelope of the single generation call, not enforced by a second corrective call, so the surfaced per-action cost and the synchronous-latency budget stay honest. The style profile is rendered to the owner in plain language, not as raw numeric scores.

**Injection and SSRF defenses.** Corpus and voice text are placed in the *data* portion of every prompt, never the instruction slot, and are delimited so a hostile corpus post cannot rewrite the model's instructions. Model output has no privileged path: anything the model produces for a post body flows through the same `validateBlogData` and sanitizer pipeline as human-authored content (ADR-008, ADR-009), and SEO/OG fields get per-field escaping and scheme validation — there is no direct DB write from a model response. The owner-pasted-URL corpus-ingestion fetch is hardened beyond the `gemini-suggest.ts` precedent: an SSRF allowlist that rejects private IPs, non-HTTPS targets, redirects to private addresses, and DNS-rebinding (validation lookup public, connect-time private), passing the fetched HTML to the extractor rather than letting the extractor fetch; plus an `AbortController` read timeout, a streaming maximum-response-bytes cap that aborts mid-stream rather than buffering an unbounded body, and an early reject on an oversized `Content-Length`. This closes both *where* the fetch connects and *how long it runs / how much it reads* — the cost-blowout and memory-exhaustion vectors on a serverless function.

**Abuse limits.** Two DB-backed, atomic, single-statement controls protect spend: a daily spend breaker (a single check-and-increment against an `ai_usage` row, decision taken from the `RETURNING` value, no read-then-write across an `await`) and a per-window request-rate limiter using the same pattern. Both return `429` *before* any Anthropic call is made, and the rate limiter also gates the corpus-ingestion route — which makes no Anthropic call but does make an outbound fetch — so a same-origin burst of ingestion requests cannot fan out into many concurrent fetches. An in-memory limiter would be unenforceable across serverless instances and is forbidden.

**CSRF posture.** Every AI mutation, spend, and ingestion route requires admin auth and rejects a cross-site POST. The spend and ingestion routes additionally fail closed when both the `Origin` and `Sec-Fetch-Site` signals are absent, rather than inheriting the generic admin endpoint's fail-open behavior in that case.

## Consequences

- **Easier**: A school that wants AI help gets it conditioned on its own voice, self-served from the admin UI with no developer involvement and no deploy — consistent with the rest of the blog's authoring model.
- **Easier**: A school that does not want AI gets a fully functional blog with the entire subsystem dormant and unreachable. The key-optional gate means "no key" is a complete, supported, zero-cost configuration, not a degraded one.
- **Easier**: Cost is visible and bounded at the point of use — per-action estimates in the UI, a hard `max_tokens` ceiling per action, a daily spend breaker, and a rate limiter — rather than discovered on a monthly bill.
- **Harder**: The school pays a recurring, usage-based external bill for as long as AI is enabled. The default synchronous-Sonnet path is expected to be low single-digit dollars per month for this workload, but the Opus opt-in is materially more expensive (higher token price plus billed adaptive-thinking tokens), and any future second-pass generation would roughly double per-action cost.
- **Harder**: This is the project's largest net-new security surface, and almost none of it has prior art in the codebase: custom AES-256-GCM crypto, a new encrypt-on-write `admin_settings` endpoint, an SSRF allowlist with rebinding defense, a hardened streaming fetch, a DB-backed spend breaker, and a DB-backed rate limiter. Each must be built and maintained as security-critical, not as a convenience feature.
- **Harder**: There are two key-rotation modes and they are not interchangeable. Rotating the Anthropic key is simple — re-enter it in the admin UI, and it is re-encrypted on write under the current master key. Rotating the AES master key requires decrypting every stored sensitive blob with the old key and re-encrypting with the new key *before* the environment variable is swapped. Swapping the master key without re-encrypting silently fails closed: GCM authentication fails, the gate reports "not configured", and the entire AI subsystem disappears — operationally indistinguishable from a rotation mistake. This footgun must be loud in the runbook because the system itself cannot make it loud.
- **Trade-off**: Fail-closed-as-not-configured is the right security posture — a key that cannot be decrypted must never be used — but it is operationally confusing, because a genuine misconfiguration and a deliberate "no key" state look identical to the operator. We accept this in exchange for never operating on a key we cannot prove is intact.
- **Trade-off**: Defaulting to Sonnet 4.6 (and Haiku for inline actions) rather than the most capable model trades some draft quality for synchronous latency that fits the serverless timeout and for lower cost. Opus 4.8 remains available as an explicit opt-in, at the price of building the background-job subsystem and accepting higher spend.
- **Trade-off**: Storing the working key encrypted in the database protects it at rest but does not protect the AES master key, which still lives in a Netlify environment variable. DB encryption narrows the exposure (a database dump alone does not yield a usable key) without eliminating the root-secret dependency.

## Open Questions and Prerequisites

- **Key storage mode (owner decision).** The default, assumed here, is the encrypted-in-`admin_settings` design with an admin-UI key entry. If the owner instead chooses a plaintext Netlify environment variable with no admin UI, the consequence is a smaller, simpler diff — no `crypto.ts`, no key-entry UI, no new write endpoint, and no custom crypto to own — at the cost of requiring a redeploy to rotate the key and no in-app key management. The plan proceeds on the encrypted default unless the owner says otherwise.
- **AI generation tier (owner decision).** The default is synchronous Sonnet 4.6, which keeps the Phase scope small (no background jobs, no poll endpoint, no polling UI). The opt-in is asynchronous Opus 4.8, which produces the best drafts but mandates a net-new background-job subsystem and a higher, thinking-inclusive cost. The plan proceeds on the synchronous-Sonnet default.
- **Netlify plan tier (hard prerequisite).** Synchronous functions cap at 10 seconds by default and 26 seconds only on higher tiers. The `gemini-suggest.ts` 24-second figure is an outbound-fetch abort, not proof the platform allows a 24–26-second synchronous function. The site's tier and any 26-second extension must be confirmed *in writing before this phase's implementation begins*, because the cap gates the synchronous default itself: a 1500–2000-token Sonnet draft can exceed 10 seconds, and if only the 10-second tier is available, the draft action must route to the background-job path regardless of the model choice.

See ADR-008 (DB-backed blog), ADR-009 (storage and editor), `docs/specs/blog.md` (AI/voice spec), and the Blog V2 implementation plan for the per-phase build sequence, test taxonomy, and the operational runbook covering key rotation, the spend breaker, and the rate limiter.
