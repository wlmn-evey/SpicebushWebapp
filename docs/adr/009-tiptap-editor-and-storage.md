# ADR-009: TipTap Editor with HTML Storage over Markdown Round-Trip

**Date**: 2026-06-06 (HTML-storage override 2026-06-07)
**Status**: Accepted (revised — supersedes the 2026-06-06 Markdown round-trip decision per owner override 2026-06-07)

> **Owner override 2026-06-07.** This ADR originally decided Markdown round-trip storage (Option B). The owner overrode that: *"fix the plan to produce the fully functional html data like tiptap wants. I would rather have it correct."* The decision is now **TipTap HTML storage**. The Context below preserves the original fork analysis (so the reversal is auditable); the Decision, migration, sanitizer, and Consequences sections are rewritten for HTML storage. This is the better engineering choice, not a concession: TipTap is HTML-native and the markdown round-trip was the fragile bolt-on. The security guarantee is preserved by keeping **render-time sanitization as the trust boundary** against a bounded V2 DOMPurify config.

## Context

ADR-008 reintroduced the blog as DB-backed content authored at `/admin/blog`, with post bodies stored as raw markdown in the `data.body` JSONB key (not a column) and rendered through a single frozen pipeline: `marked` → `DOMPurify.sanitize(STRICT_CONFIG)` in `renderPostBody` (`app/src/lib/blog-content.ts`), surfaced through the hand-rolled `.blog-body` CSS in `app/src/pages/blog/[slug].astro`. V1's authoring surface is a plain `<textarea>` plus a server-rendered preview. Six legacy markdown posts are live with stable URLs.

Blog V2 brings the full `spec/blog-cms` featureset into this live V1. The owner has settled on TipTap as the rich-text editor (a prior pick, reaffirmed 2026-06-06, not revisitable). What ADR-008 did not decide, and what this ADR must, is how a TipTap editing surface persists into `data.body` — and the choice has security and migration consequences the V1 invariants constrain.

Two storage forks were considered:

- **TipTap HTML storage** — persist the editor's native HTML output into `data.body`. Full WYSIWYG fidelity for every TipTap construct (underline, text-align, tables), no serialization round-trip to lose information.
- **TipTap with Markdown round-trip storage (Option B)** — persist markdown. TipTap's `@tiptap/markdown` `MarkdownManager` parses stored markdown into the editor on load and serializes back to markdown on save; the existing `marked` → DOMPurify render pipeline is preserved unchanged. "No Markdown serialization" applies only to constructs that markdown cannot represent (underline, text-align), which are therefore dropped — not to body storage, which remains markdown.

The deciding constraints are the V1 invariants: the 6 live posts keep their URLs and content; sanitizer rigor must be equivalent or stronger; the faithful "Preview as visitor" must render through the real public pipeline, not the editor canvas. HTML storage converts all 6 posts from markdown to HTML and widens the XSS trust boundary to TipTap's HTML output, requiring a bounded DOMPurify re-audit against that output. Markdown round-trip storage would keep `data.body` as markdown and the sanitizer frozen. *(The original 2026-06-06 decision chose markdown round-trip on these grounds; the owner overrode it 2026-06-07 — see the banner above. The Decision section reflects HTML storage, with the invariants honored by a verified conversion (content preserved by rendered-output equivalence) and a bounded, render-time-guarded `STRICT_CONFIG_V2`.)*

## Decision

Adopt **TipTap as the editor (owner's pick) with HTML storage**. Post bodies are TipTap's HTML in `data.body`. On load, `editor.commands.setContent(storedHtml, { parseOptions: { preserveWhitespace: 'full' } })` hydrates the editor; on save, `editor.getHTML()` is sanitized (write-time hygiene) and persisted. The render path becomes **stored HTML → `DOMPurify.sanitize(STRICT_CONFIG_V2)` → `.blog-body`**; `marked` is no longer in the render path (it runs only inside the one-time conversion migration below). This ADR supersedes ADR-008's `<textarea>` authoring surface and its markdown storage; ADR-008's `.blog-body` render contract and the render-time-sanitization principle stand.

**Render-time sanitization is the trust boundary and stays the trust boundary.** Storing HTML does NOT shift sanitization to write-time-only: every render re-sanitizes, so a config tightening or a write-path bug can never serve stored XSS. Sanitize-on-write at the insertion boundary (human or AI) is additional hygiene, never the sole gate.

Because storing HTML makes the full WYSIWYG construct set first-class, **underline (`<u>`), text-align, and tables are first-class** — there is no markdown-serializability constraint and no markdown-source toggle. To keep the trust boundary small and **class-based, not style-based** (owner preference): text-align ships via a custom `TextAlign.extend()` that overrides both `renderHTML` (emit `class="text-left|center|right|justify"`) and `parseHTML` (read that class), so the inline `style` attribute is never needed; tables are configured `resizable: false` so no inline `min-width`/`colwidth` style is emitted. The faithful "Preview as visitor" renders the stored HTML through the real `.blog-body` pipeline (`renderPostBody`), not the editor canvas and not `.prose` (`@tailwindcss/typography` is not installed; `.prose` is unstyled here).

### Migration of the 6 live posts

A **one-time markdown→HTML conversion** runs each live post's markdown `data.body` through the existing `marked` renderer → `DOMPurify.sanitize(STRICT_CONFIG_V2)` → stored as HTML `data.body`. It is gated by **rendered-output equivalence**, mechanically defined: the default is byte-equality, and before comparing, BOTH sides have ONLY a bounded enumerated normalization allowlist applied — (1) trim a single trailing newline, (2) collapse insignificant inter-tag whitespace, (3) normalize void-element self-closing syntax (`<hr>`/`<br>`). Any difference outside that list FAILS the gate; the list may NEVER drop or add an element (so a `<br>` can never be "normalized away"), so it cannot launder content loss. "Documented-normalization-equal" means exactly byte-equal-after-these-three-rules, not an open-ended escape hatch.

URLs are immutable. **Rollback is mechanically real: code-revert ALONE is NOT a rollback.** The 6 bodies live in Neon `data.body`; the conversion overwrites that value in place, so reverting only the code leaves converted HTML in the DB and would serve literal `<h2>`/`<strong>` tags as text. The migration therefore FIRST snapshots each row's current live markdown into a transient `data.bodyMarkdownBackup` key (keyed by `slug`+`updated_at`) BEFORE overwriting; **rollback = a reverse migration copying that backup back into `data.body`, run together with the code-revert**. Git history (migration 015, applied manually with `ON CONFLICT DO NOTHING`) is only a STALE secondary source — any post edited via `/admin/blog` after import has diverged from it — so the pre-migration live-row snapshot, not git, is the authoritative rollback source. The backup key is transient (removed in a follow-up once the conversion is ratified); no permanent legacy-markdown sidecar key is kept in steady-state `data`.

This is a late, verified Phase-1 step: the editor, `STRICT_CONFIG_V2`, and the HTML-aware alt gate land and pass first while the public render stays on markdown→`DOMPurify(STRICT_CONFIG_V1)`; then the **data conversion and the public `renderPostBody` flip to stored-HTML→`DOMPurify(STRICT_CONFIG_V2)` ship atomically in one PR/deploy**. Because `renderPostBody` serves the public 6 posts and every merge auto-deploys, flipping the render to expect HTML before the rows are converted would serve literal markdown on a live deploy; that ordering is forbidden (conversion-first is also safe, render-first is not).

### Sanitizer re-validation — STRICT_CONFIG_V2

The render-time sanitizer is `STRICT_CONFIG_V2` = V1's `STRICT_CONFIG` plus the smallest delta that admits the TipTap construct set, audited against TipTap v3's actual HTML emission. **Hook-scoping discipline (D1-F1):** `isomorphic-dompurify` exports a single shared DOMPurify singleton and `addHook` mutates its GLOBAL hook list, so a `class`/`target`/`rel` enumeration hook registered as an import-side-effect can detach (import order, tree-shaking, a refactor sanitizing from a path that imported DOMPurify without the hook), leaving `class` an allowlisted attribute with no value restriction — and the same singleton sanitizes author bios under V1 `STRICT_CONFIG`. The body sanitizer is therefore ONE function that does `addHook → sanitize → removeHook` in the same call (`isomorphic-dompurify` v2 has no reliable dedicated-instance API), so enumeration can never detach from the body render and never leaks onto the hook-free bio path. The Phase-1 sanitizer matrix exercises the PUBLIC body-sanitize entry point (not a test that pre-registers the hook), so a missing/disordered registration fails CI. The V1 properties are preserved:

1. **No `id` attribute.**
2. **Fragments stripped.**
3. **Body URI policy** — `ALLOWED_URI_REGEXP` permits `https:`, `mailto:`, `tel:`, and site-relative URLs. This is **not** "HTTPS-only"; tightening it would break the 6 live posts' `mailto:`/`tel:`/relative links and is forbidden. Distinct from the featured-image `IMAGE_SCHEME_REGEX`.
4. **`ALLOW_DATA_ATTR` and `ALLOW_ARIA_ATTR` both `false`.**

The bounded V2 delta — and what it deliberately does NOT add:

- **Tags added:** `u` (underline), `s` (strike — TipTap v3 normalizes `<del>`/`<strike>` to `<s>`), and `colgroup`/`col` (TipTap v3 table column groups). The table family (`table`/`thead`/`tbody`/`tr`/`th`/`td`), `del`, AND `br` are already in the V1 config (`blog-content.ts:396-424`) — `br` is explicitly retained in V2 because `marked` with `gfm:true` and TipTap's default HardBreak both emit `<br>`, so dropping it would silently lose hard line breaks and break the conversion equivalence gate (D1-F5).
- **Attributes added:** `class` (restricted by the `uponSanitizeAttribute` hook to an ENUMERATED allowlist — CodeBlock `language-*` hints + the four `text-*` align classes; all other class tokens dropped); `target`/`rel` (Link defaults, enumerated by hook — `_blank`/`_self`; `noopener`/`noreferrer`/`nofollow`); and `colspan`/`rowspan` (table cells). **`colwidth` is NOT added** (D1-F3): tables are `resizable:false` so it is never emitted, `ALLOWED_ATTR` does no value validation, and TipTap's `colwidth` is a comma-list not a single number — an unused, unvalidated, mis-described attribute only widens the surface.
- **`style` is NOT added.** It stays banned. Text-align is class-based; tables are `resizable:false`. The new trust boundary is therefore: a few more tags + an enumerated `class` set + enumerated `target`/`rel` + `colspan`/`rowspan` table-cell attributes — no inline CSS at all, and no `colwidth`.

`data.body` now contains `<img>` tags (TipTap-native), so the V1 markdown-token-only alt gate (`collectBodyImageAlts`) no longer sees body images. Phase 1 replaces/augments it with a **DOM-walk over the sanitized HTML's `<img>` nodes** (missing/empty `alt` flagged) before the editor is adopted; the converted 6 posts and all new TipTap/AI body images flow through it.

**Style fallback (security-critic-gated).** If the class-based custom TextAlign proves genuinely unworkable, the only fallback is a strictly-bounded `style` path (text-align with the four enumerated values only, via a value-enumeration hook). Per the owner's class-based preference, the security critic must explicitly accept any `style`-allowing path before it ships; the default and current decision is `style` fully banned.

AI output has **no privileged path**: it emits constrained HTML and flows through `validateBlogData` + the same `DOMPurify(STRICT_CONFIG_V2)` + render-time re-sanitization as human content.

### As-built notes (Phase-1 implementation)

These details surfaced during the build and are authoritative for the code (`app/src/lib/blog-html.ts`, `blog-editor-extensions.ts`); they refine, not change, the decision above:

- **`ADD_URI_SAFE_ATTR` is required.** Setting `ALLOWED_URI_REGEXP` makes DOMPurify validate EVERY non-URI-safe attribute value against that regexp — which silently strips `colspan`/`rowspan`/`target`/`rel` (their values are not URIs). They are marked URI-safe via `ADD_URI_SAFE_ATTR: ['class','target','rel','colspan','rowspan']` so the regexp applies only to the true URI attributes (`href`/`src`); the `uponSanitizeAttribute` hook still restricts `class`/`target`/`rel` values. (`class` is URI-safe by default; listed for explicitness.) Verified `javascript:` is still stripped on `href`.
- **`data:` is blocked in the hook, not by the regexp.** DOMPurify accepts `data:` on its default image tags (`img`/`source`/…) INDEPENDENTLY of `ALLOWED_URI_REGEXP`, so the regexp alone does not enforce the no-`data:` policy on images. The hook rejects `data:` on `src`/`href` — the one place the regexp cannot reach — and the editor's Image node sets `allowBase64:false` as defense-in-depth. (Not script-executable, but off-policy: inline blobs / off-allowlist image content.)
- **The HTML alt walk is a dependency-free regex scan** over `<img>` tags (`collectHtmlImageAlts`), not a literal DOM walk — it runs in the node SSR runtime without a DOM dependency and is an advisory quality gate (the render-time sanitizer is the trust boundary). During the transition both the markdown-token and HTML walks run in `validateBlogData`; each no-ops on the representation it does not own.
- **The sanitizer matrix runs in the vitest `node` environment.** vitest's default jsdom sanitizes some table-cell attributes differently than Netlify's node runtime, so the matrix is pinned to node to be production-faithful (`@tiptap/html` serializes via happy-dom there; the fixture corpus is generated from the real extension set — D1-F10).
- **The editor is MOUNTED atomically in the cutover.** The island COMPONENT lands first (additive, mounted nowhere rendered, render unchanged), and is MOUNTED in the admin forms in the SAME deploy that converts the 6 posts, flips `renderPostBody`, and drops the "Write in Markdown" helptext. Everything that switches the body representation — data, render, authoring surface, helptext — flips in one deploy, so an HTML editor never coexists with a markdown render (or vice-versa).

## Consequences

- **Easier**: Full WYSIWYG fidelity for every TipTap construct — underline, text-align, and tables are first-class, with no lossy serializer and no markdown-source toggle. What the owner authors is what is stored and rendered.
- **Easier**: No round-trip dependency. `@tiptap/markdown`/`MarkdownManager` is removed entirely; there is no parse→serialize fidelity surface to maintain or to spike headless.
- **Easier**: One render path serves every author — TipTap, AI output, and the converted legacy posts are all stored HTML rendered through `renderPostBody` → `DOMPurify(STRICT_CONFIG_V2)` → `.blog-body`. AI output has no privileged write path.
- **Harder**: The sanitizer surface is no longer frozen — it widens to `STRICT_CONFIG_V2`. This is bounded and audited: a few more tags (incl. the retained V1 `br`), an enumerated `class` allowlist, enumerated `target`/`rel`, `colspan`/`rowspan` (no `colwidth`), and **no `style` attribute** (class-based text-align, `resizable:false` tables). A per-PR sanitizer matrix vs `@tiptap/html`-generated output, run through the public add/sanitize/remove body entry point, proves the V1 properties hold and the delta is exactly as enumerated.
- **Harder**: The 6 live posts require a one-time markdown→HTML conversion. Mitigated by the rendered-output-equivalence gate (byte-equal after ONLY the bounded enumerated normalization allowlist, which may never drop an element — D1-F6), a transient pre-migration live-row markdown snapshot as the authoritative rollback source (re-written into `data.body` by a reverse migration, run with the code-revert — code-revert alone is NOT a rollback; git history is only a stale secondary source — D1-F4), and running the conversion late, after the HTML render path and sanitizer are green.
- **Harder**: `data.body` now contains `<img>` tags, so the markdown-token-only alt gate is replaced by an HTML-aware DOM-walk alt gate (R2-F4, activated by this decision) before the editor is adopted.
- **Harder**: The TipTap canvas is not the public render, so the faithful preview re-renders the stored HTML through `renderPostBody`/`.blog-body`. A first-class admin React island (the repo has zero `.test.tsx` precedent) is introduced and must carry editor-region and toolbar a11y the textarea did not need.
- **Trade-off (Markdown round-trip, the superseded prior decision)**: markdown storage froze the sanitizer and avoided a conversion, but at the cost of dropping underline/text-align, deferring tables to a source toggle, and carrying the fragile `@tiptap/markdown` round-trip with its own fallback escape hatch. The owner overrode it (2026-06-07) to store the fully functional HTML TipTap emits. HTML storage accepts a bounded, render-time-guarded sanitizer widening to gain correct, complete WYSIWYG.
- **Trade-off**: TipTap is an admin-only island (~150–300 KB est., one per page) loaded behind auth and code-split, accepted for authoring ergonomics over the zero-JS textarea; bundle size is measured in Phase 1 before the checkpoint.
